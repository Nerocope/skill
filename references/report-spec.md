## 一、报告定位

| 维度 | 说明 |
|------|------|
| **类型** | 买方选型报告（Buyer's Research Report），不是技术调研 |
| **读者** | 个人用户，关注成本、易用、实际可用 |
| **核心约束** | 以用户指定的外接模型（如 DeepSeek API）为主线 |
| **核心问题** | "在给定约束下，选哪个 Agent 最合适、最省钱？" |
| **语言** | 中文，专业但不学术，面向实际决策 |

## 三、收录原则

Agent 产品正在快速增加，报告不追求全量收录。主榜只纳入两类对象：一类是个人用户最可能遇到、讨论热度高、产品形态成熟的主流 Agent；另一类是虽然相对冷门，但对"个人使用 + 外接模型 + 成本控制"有明显价值的工具。

| 收录条件 | 判断方式 | 处理方式 |
|----------|----------|----------|
| 热门主流 | 官方产品化程度高、用户讨论多、同类报告/社区反复出现 | 进入原生体验对照 |
| 个人高相关 | 个人可直接安装或注册使用，不依赖企业流程 | 进入个人主榜 |
| 外接模型强相关 | 能直接填 API Key / Base URL，或官方支持接入 | 进入核心候选 |
| 冷门但高价值 | 名气不一定最大，但能解决明确个人场景且成本可控 | 保留，标注适用边界 |
| 企业/行业专用 | 强在 CI/CD、审计、权限、行业流程 | 只进入边界说明 |

## 四、证据分级标准

```
P0 — 官方定价页、官方文档、官方套餐页
     → 用于：定价、接口规格、BYOK 限制、套餐权益
     → 规则：P0 为最终裁决依据，P0 与 P2 冲突时以 P0 为准

P1 — GitHub 官方仓库、官方 Blog、产品官网
     → 用于：版本号、功能特性、开源协议、发布日期
     → 规则：P1 用于确认产品现状，但不作为定价依据

P2 — 第三方评测、科技媒体报道
     → 用于：用户量、DAU、市场热度、行业背景
     → 规则：P2 不作为最终裁决依据，须标注"截至日期+来源"

P3 — 社区讨论、个人博客、Reddit/V2EX/Twitter
     → 用于：用户反馈、主观体验
     → 规则：P3 仅作参考，标注"仅供参考，不作为决策依据"
```

### 每条来源必须包含：
- 分级标签 `[P0]` / `[P1]` / `[P2]` / `[P3]`
- 作者/组织 + 标题/描述
- 可点击的完整 URL
- （可选）访问日期

### 来源 HTML 格式：
```html
<li id="cite-N">
  <span class="src-title">[P0] Author/Org, Title. Description.</span>
  <a class="src-url" href="https://..." target="_blank" rel="noopener">https://...</a>
</li>
```
Inline 引用：`<sup><a href="#cite-N">[N]</a></sup>`

## 五、评分框架

### 六维度加权评分（满分 5 分）

| 维度 | 权重 | 评分标准 |
|------|------|----------|
| 外接模型/BYOK 适配 | **25%** | 5=直接填 API Key 即可用；4=官方支持但需配置；3=部分支持；2=需代理/间接方式；1=不支持 |
| 任务产出质量 | **20%** | 5=成品可直接交付；4=产出质量高但需少量修改；3=草稿级；2=产出不稳定；1=产出不可用 |
| 成本效率 | **20%** | 5=免费+BYOK；4=低价订阅+BYOK；3=中价订阅；2=高价订阅；1=极贵 |
| 工具/生态能力 | **15%** | 5=MCP+插件+连接器全覆盖；4=主要工具链完善；3=基本工具可用；2=工具链不完整；1=无工具链 |
| 易用性 | **10%** | 5=开箱即用；4=简单配置；3=需要文档；2=技术门槛高；1=极难配置 |
| 成熟度 | **10%** | 5=产品化成熟、迭代稳定；4=功能完整、偶有 Bug；3=基本可用；2=早期阶段；1=不稳定 |

### 评分须知：
- 每个维度给出具体理由，不能只写数字
- 同分产品需注明差异点
- 标注评分日期，提醒读者时效性

## 七、质量检查清单

### 结构检查
- [ ] 17 节完整，无遗漏
- [ ] TOC 可点击跳转，每个 href 对应一个 id
- [ ] 编号连续（0, 0.5, 1, 1.5, 2...14）

### 来源检查
- [ ] 每条来源标注 [P0]/[P1]/[P2]/[P3]
- [ ] 每个 inline 引用 `<sup><a href="#cite-N">[N]</a></sup>` 有对应的 `<li id="cite-N">`
- [ ] 没有孤立的 cite ref（有链接无条目）或 cite id（有条目无引用）
- [ ] 所有 URL 可点击（`<a href="..." target="_blank">`）

### 内容检查
- [ ] 无 AI 过程痕迹。搜索并删除以下关键词：
  - "千问建议"、"千问"、"本轮修改"、"本轮"、"上一版"、"上一轮"
  - "我是否"、"我做"、"你当前"、"做本报告"、"提示词"、"试用"
  - "AI思考"、"AI 思考"、"智能体思考"
- [ ] 无口语化表达："不想折腾"、"终端党"、"懒得管"、"搞不定"、"劝退"等
- [ ] 所有价格标注"截至 YYYY-MM-DD"
- [ ] P0 与 P2 冲突时以 P0 为准，P2 标注"未在官方来源确认"

### 数据检查
- [ ] 外接模型价格来自 P0 官方定价页
- [ ] 各 Agent 版本号来自 P1 GitHub 仓库
- [ ] 评分表每格有具体理由，不只写数字
- [ ] 用户真实账单数据正确引用

## 八、常见陷阱与对策

| 陷阱 | 表现 | 对策 |
|------|------|------|
| P0/P2 混淆 | 把新闻报道的峰谷价当作官方定价 | P0 官方定价页为准，P2 新闻标注"未在官方来源确认" |
| 版本号过时 | 使用博客文章中的旧版本号 | 版本号只从 P1 GitHub Releases 页面获取 |
| 遗漏 Agent | 只覆盖 6-7 个产品，生态不完整 | 按桌面/编码/自动化/原生对照四组分类，每组至少 2-3 个候选 |
| 缺少排除说明 | 只推荐，不解释为什么不选其他 | 每个场景增加"避免"列，增加"排除项说明"callout |
| 缺少国内可用性 | 忽略网络/支付/注册门槛 | 独立一节，四维矩阵（网络/支付/注册/中文支持） |
| 缺少路线选择 | 只分原生 vs 外接 | 增加开源+API vs 商业订阅 vs 混合三条路线 |
| 缺少数据时效 | 价格和功能没有截止日期 | 每个价格/功能标注"截至 YYYY-MM-DD" |
| AI 过程痕迹 | 对话中写的"本轮修改"、"千问建议"等出现在正式报告里 | 发布前搜索关键词清理（完整列表见 §七 内容检查） |
| 企业/个人混淆 | 把 Harness、企业版 Dify 等放在个人榜单 | 独立"企业边界"一节，明确划清 |
| 定位图无坐标 | 只画象限不写数值 | 给每个产品标注具体 X/Y 坐标（0-100），附坐标表 |

## 九、搜索关键词模板

### 中文搜索
- `[模型名] API 定价` 或 `[模型名] 官方价格`
- `[Agent名] github` 或 `[Agent名] 开源`
- `[Agent名] BYOK` 或 `[Agent名] 自定义API`
- `[Agent名] 最新版本` 或 `[Agent名] releases`

### 英文搜索
- `[model name] pricing` or `[model name] API pricing`
- `[agent name] github`
- `[agent name] BYOK` or `[agent name] custom API key`
- `[agent name] latest version` or `[agent name] releases`

### 搜索策略
1. **P0 优先**：先搜官方定价页、官方文档
2. **P1 其次**：搜 GitHub 仓库、官方 Blog
3. **P2 补充**：搜第三方评测、媒体报道
4. 中英文各搜一轮，中文结果优先用于国内可用性判断，英文结果优先用于版本和技术细节

## 十、原生体验对照默认覆盖列表

§5（原生与外接对比）至少应覆盖以下 Agent，具体根据用户场景增减：

| 类别 | 默认覆盖 | 说明 |
|------|----------|------|
| 通用 Agent | ChatGPT Agent | 原生体验上限标杆 |
| 编码 Agent | Claude Code, Cursor | 原生编码体验标杆 |

| IDE 编码 | TRAE Work | 国内 IDE 编码 + 文档协作 |

如果用户有明确指定的其他 Agent，也纳入此节。
